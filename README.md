# Notification Preferences Service

Небольшой сервис на TypeScript/Node, который служит единым источником правды о том,
какие типы уведомлений и по каким каналам можно отправлять конкретному пользователю.
Для любой комбинации `(пользователь, тип уведомления, канал, регион, время)` он
возвращает решение allow/deny, объединяя четыре источника: системные дефолты,
индивидуальные настройки пользователя, глобальные политики и quiet hours.

## Быстрый старт

Нужны Node 20+ и Docker.

```bash
cp .env.example .env
npm install

# Поднять PostgreSQL 16 на localhost:5432, база "notifications"
docker compose up -d

# Приложение читает DATABASE_URL. Он уже есть в .env; экспортируйте его для
# CLI-скриптов (migrate/seed), если не подгружаете .env в текущую сессию.
export DATABASE_URL=postgres://postgres:postgres@localhost:5432/notifications

npm run migrate   # создать таблицы
npm run seed      # загрузить матрицу дефолтов и одну пример-политику

npm run dev       # tsx watch на src/index.ts
# либо production-режим:
npm run build && npm start
```

Сервер слушает порт `PORT` (по умолчанию `3000`). `LOG_LEVEL` управляет выводом
pino (`info` по умолчанию; в dev-режиме читаемый pretty-вывод). `DATABASE_URL` —
единственная обязательная переменная, при её отсутствии запуск падает сразу.

## Запуск тестов

Юнит-тесты покрывают чистую доменную логику и не требуют базы:

```bash
npm run test:unit
```

Интеграционные тесты прогоняют HTTP-слой и репозитории на реальном PostgreSQL.
Укажите им отдельную базу через `TEST_DATABASE_URL`:

```bash
docker compose exec db psql -U postgres -c "create database notifications_test"

TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/notifications_test \
  npm run test:integration
```

Прогнать всё сразу:

```bash
npm test
```

## API

Полный машиночитаемый контракт лежит в [`docs/openapi.yaml`](docs/openapi.yaml)
(OpenAPI 3.1), его можно вставить в Swagger Editor. Ниже краткая сводка.

Все тела запросов и ответов в JSON. Ошибки валидации возвращают `400` с телом
`{ "error": { "code", "message", "details" } }`; неожиданные ошибки — `500`.

### Доменный словарь

- Каналы: `email`, `sms`, `push`, `messenger`
- Типы уведомлений: `transactional`, `security`, `system`, `marketing`, `promotional`
- `transactional`, `security` и `system` чувствительны ко времени и игнорируют quiet hours.

### `GET /users/:id/preferences`

Возвращает эффективную матрицу настроек пользователя (дефолты с применёнными
переопределениями) и quiet hours. Поле `source` принимает значения `default`,
`user` или `unset`.

```bash
curl http://localhost:3000/users/u123/preferences
```

```json
{
  "userId": "u123",
  "preferences": [
    { "notificationType": "transactional", "channel": "email", "enabled": true, "source": "default" },
    { "notificationType": "marketing", "channel": "email", "enabled": true, "source": "user" }
  ],
  "quietHours": { "timezone": "Europe/Berlin", "start": "22:00", "end": "08:00" }
}
```

Пользователь неявный: любой id резолвится в дефолты, пока у него нет
переопределений, поэтому отдельного шага «создать пользователя» нет.

### `POST /users/:id/preferences`

Делает upsert переопределений и/или quiet hours и возвращает тот же формат, что и
GET. Оба верхнеуровневых ключа необязательны. Семантика quiet hours:

- ключ отсутствует: quiet hours не меняются
- ключ равен `null`: quiet hours очищаются
- ключ — объект: quiet hours заменяются

```bash
curl -X POST http://localhost:3000/users/u123/preferences \
  -H 'content-type: application/json' \
  -d '{
    "preferences": [
      { "notificationType": "marketing", "channel": "email", "enabled": true }
    ],
    "quietHours": { "timezone": "Europe/Berlin", "start": "22:00", "end": "08:00" }
  }'
```

Время задаётся в формате `HH:mm` (24 часа). Таймзона должна быть валидной зоной IANA.

### `POST /evaluate`

Ключевое решение. По кандидату на отправку возвращает, можно ли его отправить и почему.

```bash
curl -X POST http://localhost:3000/evaluate \
  -H 'content-type: application/json' \
  -d '{
    "userId": "u123",
    "notificationType": "marketing",
    "channel": "sms",
    "region": "EU",
    "datetime": "2026-06-06T21:30:00Z"
  }'
```

```json
{ "decision": "deny", "reason": "blocked_by_global_policy" }
```

`datetime` — это метка времени в ISO-8601; `region` — произвольная строка
(внутри нормализуется к верхнему регистру).

#### Приоритет правил и причины

Правила применяются в фиксированном порядке; побеждает первое, которое запрещает:

1. Сработала глобальная политика: `blocked_by_global_policy`
2. Пользователь отключил вручную: `disabled_by_user`
3. Отключено дефолтом: `disabled_by_default`
   (или `not_configured`, если для пары нет дефолта)
4. Quiet hours, для типов без исключения: `quiet_hours`
5. Иначе `allow` с причиной `allowed`

Полный набор значений `reason`: `blocked_by_global_policy`, `disabled_by_user`,
`disabled_by_default`, `quiet_hours`, `not_configured`, `allowed`.

## Архитектура

Код разбит на три слоя, зависимости направлены внутрь.

**Domain** (`src/domain`) содержит типизированную модель (каналы, типы уведомлений,
настройки, политики, quiet hours) и чистую логику принятия решения. `evaluate()` —
чистая функция: принимает запрос и полностью загруженный контекст
(`defaults`, `userOverrides`, `quietHours`, `policies`) и возвращает решение без
ввода-вывода. Благодаря этому правила (приоритеты, исключения по quiet hours,
переход окна через полночь) полностью покрываются юнит-тестами без базы.
Интерфейсы репозиториев («порты») тоже живут здесь, поэтому домен не зависит от `pg`.

**Application** (`src/application`) оркестрирует порты. Сервисы загружают данные,
нужные `evaluate()` и `resolvePreferences()` (параллельно), вызывают чистые функции
и пишут структурированные логи. Собственных бизнес-правил у них нет.

**Infrastructure** (`src/infrastructure`) — это внешний мир: репозитории PostgreSQL,
реализующие доменные порты, HTTP-слой на Express, загрузка конфигурации и логгер
pino. HTTP-слой валидирует вход через zod, маппит доменную модель в формат провода
и обратно и прогоняет все ошибки через единый middleware обработки ошибок, который
переводит ошибки zod и доменные ошибки в HTTP-коды.

Основные решения:

- Чистое ядро. Вся логика решения — чистая функция над контекстом в памяти, поэтому
  корректность проверяется быстрыми юнит-тестами, а интеграционным остаётся
  подтвердить связку и SQL.
- Идемпотентность записи через upsert по состоянию. Записи настроек и quiet hours
  используют `INSERT ... ON CONFLICT DO UPDATE` по естественному ключу, поэтому
  повтор того же `POST` приводит к тому же состоянию. Отдельные idempotency-ключи на
  запрос не нужны.
- Quiet hours хранятся как минуты от полуночи плюс таймзона IANA и вычисляются через
  luxon. Окно трактуется в локальном времени пользователя и корректно обрабатывает
  переход через полночь (например, `22:00`–`08:00`); окно нулевой длины не блокирует
  ничего.
- Глобальные политики используют nullable-поля как wildcard (`notification_type`,
  `channel`, `region`). Поле `null` совпадает с чем угодно, поэтому одна строка может
  выразить и широкую («весь marketing в EU»), и узкую («marketing SMS в EU») область.
  В сиде есть один пример: marketing SMS заблокирован в EU.
- Дефолты задают полную матрицу настроек: для каждой пары `(тип, канал)` есть дефолт.
  Пользователь неявный, поэтому любой id резолвится в дефолты, пока нет
  переопределений; это избавляет от регистрации для того, что по сути является
  сервисом-справочником.
- Валидация через zod на границе HTTP оставляет домен свободным от разбора входных
  данных. Два бизнес-события логируются структурно (`preferences.updated`,
  `evaluation.decided`) плюс строка `request.completed` на каждый запрос; это
  естественные точки для счётчиков и таймеров метрик.

## Что добавил бы дальше перед продакшеном

- Аутентификация/авторизация. Сейчас API открыт; нужна service-to-service аутентификация
  и проверка, что вызывающий вправе читать/менять настройки данного пользователя.
- Метрики и трейсинг. Счётчики Prometheus по allow/deny в разрезе `reason`, гистограммы
  латентности по маршрутам и trace-id на запрос, пробрасываемый в уже существующие логи.
- Аудит-лог изменений настроек (кто, что, когда), отдельно от текущего состояния, для
  комплаенса и отладки.
- Кеширование дефолтов и глобальных политик: они меняются редко, а читаются на каждом
  evaluate; с явной инвалидацией.
- Пагинация и фильтрация в `GET /users/:id/preferences`, когда матрица вырастет.
- Admin API для управления глобальными политиками (сейчас только через сид/SQL).
- Безопасность записи: оптимистичная блокировка (проверка версии или `updated_at`) либо
  idempotency-ключи на запрос, если клиентам нужны гарантии сильнее, чем сходимость по
  состоянию.
- Усиление БД: настройка размера пула соединений, statement timeouts и прогон миграций
  как отдельный gated-шаг в CI.
- Каталог типов уведомлений как данные: заменить захардкоженные enum (и соответствующие
  SQL-констрейнты `check`) таблицей, чтобы новые типы или каналы не требовали деплоя.
- Контрактные и нагрузочные тесты в дополнение к текущему делению на unit/integration.
